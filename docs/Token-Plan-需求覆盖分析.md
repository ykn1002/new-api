# Token Plan 需求 × new-api 现状 覆盖分析

> 目的：评估《Token Plan 方案》需求，判断 new-api 现有能力能覆盖哪些、哪些需改造或新建。
>
> 结论速览：**计费内核（人民币→额度→Token）、模型定价、充值/支付、流水、统计看板、限流、代充值** 这些基础设施 new-api 已具备，多数可直接复用或小改；**真正的缺口集中在：积分有效期、积分来源分账、带赠送积分的充值档位、默认模型强制、微信支付接口、小程序账号一对一映射/自动开户、运营看板的导出与总览聚合**。

- 🟡 部分支持，需改造/补齐

- **既定口径：方案里的「积分」≡ new-api 的「自定义货币」（`QuotaDisplayType=CUSTOM`）。** new-api 内部计费单位是 **quota（整数高精度台账）**，用户不直接感知；积分是 quota 的对外展示投影：`积分 = (quota / QuotaPerUnit) × CustomCurrencyExchangeRate`。扣费/精度都在 quota 层完成，对外一律以积分呈现。

> ⚠️ 概念差异（docx 1.4「关键换算关系」+ 角色职责）：原需求设想 **三层换算** `tokens→人民币成本`、`人民币成本→人民币收入`、`人民币收入→积分`。new-api 的模型倍率本质是**「售价」**（收入侧），**没有独立的「成本」字段**——3.1 模型计费字段也只建模「输入/输出人民币单价(售价)」，无成本单价。影响：① 加价(成本→收入)只能由运营把利润直接揉进售价倍率，不单独建模；② 3.6 看板的「成本估算」需真实上游成本，new-api 按售价计费、不逐次记录上游成本，需另接渠道成本或留作待确认。建议评审确认本期是否需要独立成本核算（否则"成本估算"只能近似）。

#### 推荐方案：人民币 ≡ 美元（不使用内置支付渠道时）

如果**不使用内置支付渠道**（Stripe/易支付等），自建微信支付直接给用户加 quota，则可把内部的「USD」当作人民币使用，汇率配置回归直觉：

```
USDExchangeRate            = 1      // 原 7.3；设 1 后「1 美元单位」≡ 1 元
QuotaPerUnit               = 500000 // 保持默认（倍率 1 = 每 token 扣 1 quota，最整）
QuotaDisplayType           = CUSTOM
CustomCurrencySymbol       = "积分"
CustomCurrencyExchangeRate = 100    // 1 元 = 100 积分（不再需要 ×7.3=730）
```

**全链路验证（用方案 3.1 的算例）：**

- 充值：付 1 元 → 加 `1 × 500000 = 500000` quota → 展示 `(500000/500000)×100 = 100 积分` ✅
- 模型 A 定价（输入 2 元/1K、输出 6 元/1K）：
  - 输入每 token = `0.002 × 500000 = 1000` quota → `ModelRatio = 1000`
  - 输出是输入的 3 倍 → `CompletionRatio = 3`
- 扣费（输入 1500 + 输出 800）：
  - quota = `1500×1000 + 800×1000×3 = 3,900,000`
  - 折算 = `3,900,000 / 500000 = 7.8 元` → **780 积分**，与方案「扣减 7.8 元」算例自洽 ✅

**注意事项：**

1. 关闭/不使用内置支付渠道（它们走 `Price=7.3` 的美元换算）；自建微信支付回调按 `quota = 付款元数 × QuotaPerUnit` 加额度。
2. 内置默认模型倍率是按上游美元成本调的，基准当人民币后会失真——需按自己产品给「默认模型」重配倍率（本就要做）。
3. 不要再用 USD 展示类型（会把「$」显示成实际人民币值），统一用 CUSTOM（积分）展示。
4. `QuotaPerUnit` 可自选，但 500000 让「倍率=每 token quota」最整，建议保持；若改需同步重算上面所有换算。

## 三、缺口汇总（按工作量与优先级）

### A. 必须新建（核心缺口）

1. **积分有效期 + 到期清零 + 多次充值顺延**（需求 3）——wallet quota 当前无有效期，需引入「积分批次」模型（批次=金额/有效期/剩余/来源）。
2. **积分来源分账（赠送/套餐/充值）+ 优先扣减顺序**（需求 3）——配合批次模型实现「赠送优先→套餐→充值」扣减与占比展示。本期套餐积分经后台配置/运营发放产生（无用户购买入口）。
3. **充值档位扩展**：从「金额+折扣」升级为「档位名称 + 金额 + 基础积分 + 赠送积分 + 有效期」（需求 2）。
4. **全局默认模型 + 禁止用户选模型**（需求 6）。
5. **微信支付接口（小程序登录已具备）**：微信支付渠道（小程序 JSAPI 下单返回 `prepay_id` + 签名参数）+ 回调验签到账。复用现有登录/余额/档位/明细接口。
6. **小程序账号一对一映射 + 自动开户**（需求 4）：复用 `UserOAuthBinding`，补「按 `mp_account_id` 查映射→命中放行/未命中自动建 User+绑定」+ 并发去重 + 信任边界校验（详见技术方案 M7）。
7. **模型规则定时生效（调价预约）**（需求 1 / docx 3.1）——支持配置规则「生效时间」，到点自动切换价格；现状改价即时生效，需新建。

### B. 改造 / 包装（已有内核，需适配）

8. **启用「积分」自定义货币展示 + 对齐充值汇率**：推荐「人民币≡美元」简化（`USDExchangeRate=1`、`QuotaDisplayType=CUSTOM`、符号「积分」、`CustomCurrencyExchangeRate=100` 即 1元=100积分），自建微信支付直接加 quota。无需改动 quota 内核（需求 2，详见该节「推荐方案」）。

10. **流水表补字段**：来源(source)、操作后余额(balance_after) 列 + 类型筛选（需求 3）。
11. **运营看板补「导出 + 总览聚合（累计充值/活跃用户）」**（需求 5）。
12. **汇率配置权限收紧到研发/超管**（需求 2）。
13. **余额预警改造**：①阈值从绝对值扩展为支持**百分比（剩余<20%，可配）**；②低余额除通知用户外，**同时通知运营**（需求 3 / docx 3.3、4.3）。

## 五、覆盖度评估与总结

**量化口径**：统计本期范围内（已排除「四、本期明确不做」的流量管控、套餐购买等）约 45 个功能点，按 ✅=1 / 🟡=0.5 / ❌=0 计分。

| 类别 | 数量 | 占比 | 说明 |
|---|---|---|---|
| ✅ 完全可用 | 约 21 项 | ~47% | 模型输入/输出定价、充值订单+多渠道支付、自助/代充值、套餐后台配置、多维统计看板、限流等 |
| 🟡 部分支持/小改即可 | 约 17 项 | — | 积分自定义货币展示与汇率对齐、充值档位扩展、小程序下单/映射、流水补字段、百分比预警等 |
| ❌ 需新建 | 约 7 项 | ~16% | 积分有效期+顺延、来源分账+来源卡片、全局默认模型、规则定时生效、数据导出 |

**加权覆盖 ≈ 65%**（= (21 + 17×0.5) / 45）。

**结论**：new-api 的**计费内核与运营后台基础设施**已覆盖约 65% 的本期能力，且大量 🟡 项只是「在已有内核上做语义包装/字段补齐」，真正从零新建的硬缺口约 16%，**集中在「积分产品化账本」**——即积分有效期、到期清零顺延、按来源分账与优先扣减（需引入「积分批次」模型，技术方案 M2）。

其余重点新建项：全局默认模型/禁止选模型、微信支付接口、小程序账号一对一映射/自动开户、模型规则定时生效、看板数据导出。配置/包装类（积分=自定义货币、人民币≡美元、两位小数）成本低。**一处待评审澄清**：是否需要独立成本核算（成本→收入分层，见 B'）。
